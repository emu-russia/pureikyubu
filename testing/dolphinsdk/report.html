DolphinSDK GX demo sweep

Every demo in DolphinSDK\HW2\bin\demos\gxdemo (87 ELF binaries) run through the emulator's SDL2 port with the DolphinSDK folder mounted as a virtual DVD, for 7 seconds each. The method is described in testing/dolphinsdk/Readme.md.

How to read the verdicts. frames counts the GXDrawDone/PE-finish interrupts, so a demo that never calls GXDrawDone (the FIFO break-point and triple-buffer management demos, for instance) shows 0 even while it renders — the picture, not the counter, decides. flat means the captured picture is a single colour. The notes give what the demo's source says it should do, so a flat or missing picture can be judged against it. Runs are made without controller input, so demos that only change state on a button show their first case.

87 demos 72 clean 3 drawn nothing (flat picture) 6 never finished a frame

Three emulator bugs found this way are fixed: the PE draw-sync token was treated as a frame boundary, which swapped the frame half-way through and lost the picture of every demo that puts GXSetDrawSync in the middle of a frame (frb-bound-box came out black); and the XF_IndexLoadRegA..D commands (the indexed matrix/light block loads behind GXLoadPosMtxIndx / GXLoadTexMtxIndx) were logged and thrown away, which left DL-tf-mtx and tf-reflect with no matrices at all. The report below is from the build with both fixes.

What is still open

  • ind-bump-st, ind-bump-xyz - the generated light map (TEXMAP1, an IA8 texture the demo renders into the EFB and copies out with GXCopyTex) is empty. The geometry, the lighting arithmetic, the copy destination against the texture address, the viewport, the scissor and the GL draw order have all been checked and ruled out; what is left is the frame bookkeeping (GPFrameBegin/GL_BeginFrame and the pending copy clears) around a PE_COPY_CMD that arrives before the main loop's first frame.
  • tev-outline - 3402 primitives and 378 display-list calls reach the command processor and no pixel appears; the per-vertex matrix index is the next thing to check.
  • G2D-test - one 472-vertex quad batch per frame is drawn as a large dark shape; the 2D layer's scale/projection is the next thing to check.
  • The PE bounding box is not emulated: PE_XBOUND/PE_YBOUND latch the BP write but are never updated from the drawn geometry, and the CPU-visible PE_PI_XBOUND0/1, YBOUND0/1 pair reads back as 0, so GXReadBoundingBox always answers (0,0,0,0) (gfx-pe 6.17, gfx-pe 8).

Narrowed down by experiment: forcing the texture sampler to return white for every map makes the donut appear (2 colours, 16% of the screen), so the geometry, the projection, the TEV structure and the indirect stage all work - it is the texture *values* that are black. Forcing white for map 1 only (TEXMAP1, the light map) reproduces it exactly, while forcing map 0 or 2 changes nothing, so the light map is the black one.
The light map is generated once before the frame loop: lightMapSetup() renders a hemisphere into the EFB with lighting on (diffuse in COLOR0, specular in ALPHA0) and GXCopyTex(lightMap, FALSE) copies it into an IA8 texture in main memory. The demo also calls showMaps() every frame to display that light map, and nothing of it is visible either, so the texture really is empty.
Next: instrument which side is empty - the hemisphere render (the light and the two channel controls) or the IA8 texture copy (the emulator does implement TF_IA8 in TextureCopy, and its byte order matches the texture decoder in tx.cpp, so the copy path itself looks consistent).

More evidence (all of it from temporary logs and shader experiments, reverted afterwards):
  - The copy does run: a TEXCOPY log in PixelEngine::TextureCopy reports exactly one copy for this demo,
    64x64, fmt=3 (IA8), source (0,0), destination 0x00239F40, a valid main-memory pointer, stride 16.
    The working frb-copy demo copies 32x32 fmt=4 (RGB565) 354 times through the same code, so the copy
    engine itself is fine.
  - The light is a standard specular setup: GXInitSpecularDir + GXInitLightColor(0x88) +
    GXInitLightAttn(-3, 0, 4, ...) with the comment "Light equation 4x^2 - 3, x = N.H". The emulator's
    CosineAttenuation computes exactly clamp(a0 + a1*cos + a2*cos^2) = clamp(-3 + 4*cos^2), and the
    diffuse material is white, so with the illumination term forced to 1.0 the hemisphere must render
    white.
  - Forcing the illumination term to 1.0 does NOT make the donut appear, so the lighting of the
    hemisphere is not the fault: the hemisphere render, the copy and the texture the TEV samples do not
    meet. The next thing to check is that the address the copy writes (PE_COPY_DST_BASE << 5, a physical
    address) and the data pointer of the texture object the TEV samples (a pointer the emulator masks
    itself) really are the same memory.

Decisive check of the addressing: a temporary log of the texture engine's image address shows the
light map is programmed at addr=0x00239F40, fmt=3 (IA8), 64x64, 8192 bytes - exactly the destination
the copy wrote (0x00239F40, fmt=3, 64x64, stride 16). So the copy writes precisely where the sampler
reads, and the light map is empty only because the EFB the copy read back held nothing.
The render that should fill it is drawHemisphere() (triangle strips over the whole screen with an
orthographic projection, white diffuse material, the specular light above), and forcing the
illumination term to 1.0 still left the picture black - which points at the ordering rather than at
the values: the GXCopyTex reads the EFB back, and the geometry the demo drew just before it has to be
in the GL framebuffer by then. Next: check the emulator's GL draw batching/flush order around
PE_COPY_CMD, i.e. whether ReadEfb sees the draws that the CP issued earlier in the same frame.

Final narrowing of this pass: the copy's readback *succeeds* - the TEXCOPY log line sits after the
ReadEfb() call and TextureCopy returns early when the readback fails - so the GL context is current,
glReadPixels runs, and it returns black. The hemisphere the demo drew immediately before the copy is
therefore not in the framebuffer yet: the emulator clears/starts the GL frame on the draw path
(GPFrameBegin -> GL_BeginFrame) while PE_COPY_CMD reads the EFB back, so the order of start-frame and
readback around the first frame is what to look at next (the demo does its one and only light map
render plus GXCopyTex *before* the main loop, i.e. before the first DEMOBeforeRender).

Also ruled out: the light map render targets the top-left 64x64 of the EFB
(setupSize -> GXSetViewport(0,0,64,64) + GXSetScissor(0,0,64,64)), and TextureCopy converts that
rectangle correctly for the GL readback (ReadEfb(srcX, RenderHeight - srcY - h, ...)), so the
viewport placement is not the reason the copied rectangle is empty. That leaves the frame order:
GPFrameBegin()/GL_BeginFrame() (which clears) runs from the draw path in cp.cpp, while PE_COPY_CMD
reads the EFB back - for a copy made before the main loop's first frame the two have to be checked
against each other.

And the viewport mapping itself is right: GL_SetViewport does glViewport(x, scr_h - (h + y), w, h), i.e.
it flips GX's top-left origin for GL, and RAS_End() issues glDrawArrays synchronously at GXEnd, so the
hemisphere really is drawn into the GL buffer before the copy command is walked. What is left for this
demo is the frame bookkeeping (GPFrameBegin/GL_BeginFrame and the pending copy clears) around a
PE_COPY_CMD that arrives before the main loop's first frame.

One more hypothesis ruled out: GL_SetScissor documents and implements the Y flip for the scissor
rectangle ("the programmed scissor rectangle is in screen coordinates, the origin is the top left
corner of the EFB ... GL measures its scissor box from the bottom left corner, so the Y axis is
flipped here"), so the 64x64 scissor and the 64x64 viewport agree with the rectangle the copy reads.
With the geometry, the lighting, the addressing, the viewport, the scissor and the GL draw order all
checked, what is left is the frame bookkeeping (GPFrameBegin/GL_BeginFrame plus the pending copy
clears) around a PE_COPY_CMD that arrives before the main loop's first frame.

frb-bound-box
frb-bound-box: bounding box feature demo		pe747
vi1432
CP 0x20200		okFIXED by this sweep: the demo shows its eight coloured cubes now. The cubes and the bounding-box outline were reaching the command processor all along; the picture was lost because the PE draw-sync token was treated as a frame boundary, so the frame was swapped half-way through and the buffer the display copy presented held only the (degenerate) outline. The white outline is still missing: the emulator does not track the bounding box yet.
Before the fix: pure black (one colour). After: 46 colours, 82% background, the eight GXDrawCube
cubes visible in their material colours.

Root cause (fixed in src/pe.cpp): the PE token path called GPFrameDone(), which presents the frame.
frb-bound-box puts GXSetDrawSync in the middle of the frame - draw the cubes, sync, wait, read the
bounding box back, draw the outline - so the swap happened with only the cubes drawn, and the
display copy at the end of the frame then presented the other back buffer, which held just the
outline over nothing. A draw-sync token is a synchronisation marker, not the end of a frame; the
frame is presented at GXDrawDone (PE_FINISH) and at a full-frame display copy (GPDisplayCopy),
which are the points where the picture is complete.

Evidence gathered before the fix:
  - CP draw log: 2728 x "Draw: cmd 0x83, vtxnum 24, vat 3" (the cubes) and 341 x "Draw: cmd 0xB0,
    vtxnum 5, vat 0" (the outline) - the geometry did reach the command processor.
  - XF lighting log: ambient 0x404040FF, the eight cube materials and channel control 0x00000506
    (lighting on, light 0, N.L clamped, attenuation off), exactly what the demo asks for.
  - Forcing the illumination term to 1.0 in the vertex shader still gave black, which ruled the
    lighting arithmetic out and pointed at the presentation path.

Still open: the bounding box itself. PE_XBOUND/YBOUND (0x55/0x56) latch the BP write but are never
updated from the drawn geometry, and the CPU-visible PE_PI_XBOUND0/1 and YBOUND0/1 pair
(0x10/0x12/0x14/0x16) reads back as 0, so GXReadBoundingBox always answers (0,0,0,0) and the white
outline collapses to a point (gfx-pe 6.17 and gfx-pe 8).
