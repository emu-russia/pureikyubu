DolphinSDK GX demo sweep

Every demo in DolphinSDK\HW2\bin\demos\gxdemo (87 ELF binaries) run through the emulator's SDL2 port with the DolphinSDK folder mounted as a virtual DVD, for 7 seconds each. The method is described in testing/dolphinsdk/Readme.md.

How to read the verdicts. frames counts the GXDrawDone/PE-finish interrupts, so a demo that never calls GXDrawDone (the FIFO break-point and triple-buffer management demos, for instance) shows 0 even while it renders — the picture, not the counter, decides. flat means the captured picture is a single colour. The notes give what the demo's source says it should do, so a flat or missing picture can be judged against it. Runs are made without controller input, so demos that only change state on a button show their first case.

87 demos 72 clean 0 drawn nothing (flat picture) 1 never finished a frame

Three emulator bugs found this way are fixed: the PE draw-sync token was treated as a frame boundary, which swapped the frame half-way through and lost the picture of every demo that puts GXSetDrawSync in the middle of a frame (frb-bound-box came out black); and the XF_IndexLoadRegA..D commands (the indexed matrix/light block loads behind GXLoadPosMtxIndx / GXLoadTexMtxIndx) were logged and thrown away, which left DL-tf-mtx and tf-reflect with no matrices at all. The report below is from the build with both fixes.

What is still open

  • ind-bump-st, ind-bump-xyz - the generated light map (TEXMAP1, an IA8 texture the demo renders into the EFB and copies out with GXCopyTex) is empty. The geometry, the lighting arithmetic, the copy destination against the texture address, the viewport, the scissor and the GL draw order have all been checked and ruled out; what is left is the frame bookkeeping (GPFrameBegin/GL_BeginFrame and the pending copy clears) around a PE_COPY_CMD that arrives before the main loop's first frame.
  • tev-outline - 3402 primitives and 378 display-list calls reach the command processor and no pixel appears; the per-vertex matrix index is the next thing to check.
  • G2D-test - one 472-vertex quad batch per frame is drawn as a large dark shape; the 2D layer's scale/projection is the next thing to check.
  • The PE bounding box is not emulated: PE_XBOUND/PE_YBOUND latch the BP write but are never updated from the drawn geometry, and the CPU-visible PE_PI_XBOUND0/1, YBOUND0/1 pair reads back as 0, so GXReadBoundingBox always answers (0,0,0,0) (gfx-pe 6.17, gfx-pe 8).

SoftGPU: the same demos through the software GFX pipeline

The right-hand column of the table is the same demo rendered by the software (CPU) pipeline of issue #384 (the GFX_PIPELINE = 1 configuration, see wiki/gfxsoft.md): the XF, the setup unit, the quad-based rasterizers, a real TMEM, the TEV and a pixel engine with a real EFB memory array, with the copy engine writing the XFB that the video interface scans out. No OpenGL call is involved in that path. The runs use the same method, the same settle time and the same build as the shader column.

87 captured 81 drew a picture 0 flat 6 never finished a frame 18 match the shader picture 69 differ

match/differ is the mean absolute pixel difference of the two 160x120 captures: below 6 counts as a match (the demos animate, so two runs of the same demo never match exactly), above it the two pictures are visibly different and the row is worth looking at. A demo that is already broken under the shader backend can differ in both columns without telling anything about the software pipeline.

frb-bound-box
differs (60.5; 31% of the pixels)
pe0
vi0
CP 0x201		okFIXED by this sweep: the eight cubes and the white bounding-box outline render.
Source: Framebuffer/frb-bound-box.c - the frame clears the box with GXClearBoundingBox, draws eight cubes, waits on a draw-sync token, reads the box back with GXReadBoundingBox and draws the outline from the two corners in screen space.
The PE bounding box was not emulated at all: PE_XBOUND / PE_YBOUND (0x55/0x56) latched the BP write and were never extended from the drawn geometry, and the CPU-visible PE_PI_XBOUND0/1 and YBOUND0/1 pair (0x10/0x12/0x14/0x16) read back as 0, so the outline collapsed to a point (gfx-pe.md 6.17).
It is extended now, once per primitive, with the window extent of the vertices the primitive is drawn from: the shader pipeline leaves the transform to the vertex program, so the rasterizer forms those window positions out of the same XF registers that program reads (the geometry matrix of the vertex's slot, the projection combine and the viewport scale/offset) and clamps them to the render target. A title clears the box with GXClearBoundingBox, which writes the empty range, so the two halves take care of each other with a minimum and a maximum per axis.
The box is the extent of the drawn vertices, not of the 2x2 quads the hardware walks, so a primitive that runs off the edge of the screen can leave the box a little larger than the pixels that were actually shaded.

ind-bump-st
differs (13.6; 9% of the pixels)
pe0
vi0
CP 0x201		okFIXED by this sweep: the bump-mapped donut renders (light map and all). The four showMaps() overlay quads (the light map and the bump components in the screen corners) are still missing.
Source: Indirect/ind-bump-st.c - the emulator build takes the real indirect path (four TEV stages, one indirect stage, GXSetTevIndBumpST), so the donut is the material texture modulated by the light map indexed through the perturbed normal.
Root cause (fixed in src/gfx.cpp): the GL backend's own frame-begin clear took its depth from PE_COPY_CLEAR_Z, which a title only programs when it clears through the copy engine; on the first frame that register still holds 0, so the depth buffer was cleared to the near plane and every fragment of the frame failed the compare. The light map render is in exactly that frame.
Also fixed here (src/xf.cpp): the XF vertex shader handed the GX clip-space z straight to GL. The SDK matrices scale z into the GX range (-w, 0], so only half of the depth range was used and the programmed viewport z did not describe the depth GL was given; the range is doubled (z' = 2z + w) now, the same mapping the software pipeline applies in SoftVertexToWindow.
The four showMaps() overlay quads (the light map and the bump components drawn in the screen
corners) are still missing, and the fault is in the vertex attribute read, not in the shader or the
vertex pipeline. Three minimal programs of the emulator's own tell them apart, all drawing the same
four vertices out of the same verified CPU data into a fresh VAO and VBO:
  - gl_Position from gl_VertexID at the quad's clip positions, no attribute read: draws (8128 px);
  - gl_Position from gl_VertexID, the position attribute fed into a varying arithmetically
    (clamp(pos * 0.25 + 0.5)): the primitive is dropped outright, which is what a NaN in the
    attribute does - a finite value, however large or negative, would have clamped to a colour;
  - gl_Position = pos.xy from the attribute: draws nothing, i.e. the clip positions are NaN.
A fourth program takes the demo's data out of the picture entirely: a hard-coded float[12] of exactly
the four positions the quads should have, uploaded into a buffer of its own with a stride of three
floats, drawn with the same minimal program - and it draws nothing either, while the program that
reads no attribute at all renders. The failure is therefore in the attribute fetch of the context
these draws run in, not in the demo's vertex data or the emulator's vertex pipeline.
The CPU array, the VBO (read back with glGetBufferSubData right after the upload), a tightly packed
copy of the same positions, the index buffer, the VAO attribute state read at draw time, the integer
matrix-index attributes and re-specifying the attribute pointer have all been checked and ruled out.
What makes these four draws special is still open: other demos draw 4-vertex GX_QUADS through the
same path and render (tex-invalid's grid, frb-bound-box's cubes), and tex-invalid's vertex format is
the same shape (position and texture coordinate, no normal or colour).
Still open: the four showMaps() overlay quads (the light map and the bump components drawn in the screen corners) do not rasterise. Their vertices are in the VBO, the position attribute is bound and enabled, and a quad built from gl_VertexID at the very same clip positions does draw, while gl_Position taken from the position attribute does not; the cause is not culling, the scissor, the depth test, the alpha test or the near plane.
Two further candidates were tested and ruled out. The four quads are drawn with the identity position
matrix and a vertex z of -1 under the perspective frustum renderSetup1() leaves in place
(MTXFrustum with near = 1, far = 15), so they sit exactly on the near plane (NDC z = -1): moving the
mapped depth strictly inside the clip volume (z' = 2z + 0.9999w) does not bring them back, so the
boundary is not the cause. Orphaning the vertex buffer (glBufferData instead of glBufferSubData, the
usual remedy for a driver that still reads the previous contents) changes nothing either.
Note that testing/dolphinsdk/shots/gxdemo__ind-bump-st.png is one of the captures the first sweep made
while this demo was broken (a flat black frame), so it is not a reference for what the overlays should
look like; the expectation comes from the source, showMaps() drawing four textured quads in the screen
corners before the scene.
The GL context is not the difference: logging hglrc, the device context, the current thread id, the
bound VAO and the current program at the draw shows the same values for the failing four-vertex draws
and for the twenty-two-vertex donut draw that renders in the same frame (same context, same thread,
same VAO id, same program id), so both go through exactly the same objects and the difference is the
draw itself.
The software pipeline's capture of this demo (testing/dolphinsdk/shots_soft) shows the same donut and
no corner overlays either. Both pipelines share the command processor, the transform unit and the
setup unit and differ only in the rasterizer, so the missing overlays are not a shader-backend fault -
the GL attribute experiments above were chasing an artefact of the probe programs. Reject-en
(GEN_MODE.reject_en, which GL_SetCullMode maps with a standing TODO about the two being mixed up) was
tested by forcing the cull off altogether: the overlays do not appear, so they are not culled either.
What the demo asks for is a set of single-sided quads that lie exactly on the near plane of the
perspective frustum renderSetup1() installs (MTXFrustum with near = 1, far = 15) with the identity
position matrix loaded, so the remaining question is whether the hardware keeps that geometry at all -
the demo may simply be drawing outside its own frustum, in which case the emulator is right to drop it.

Source: Lighting/lit-atn-func.c - a half-cylinder lit by a spot light at its axis, with the attenuation function under test.
Two bugs:
  - src/cp.cpp: FifoProcessor::Peek16 was declared to return a byte, so the 16-bit vertex count of a draw command was truncated to its low eight bits. This demo draws four strips of 362 vertices; enough-to-execute saw 106 and ran the command while most of its vertex data was still on its way in, so a quarter of the strip decoded as zeros. The stream buffer's back-pressure then had to be taught not to stop the reader in the middle of the command at the head (it stopped at 8 KB, less than the command needs), and the buffer is sized for the largest command a title can issue.
  - src/xf.cpp: the vertex shader negated the light direction in the spot attenuation. The SDK stores the spot axis with the opposite sign, so the cosine is dot(L, Ldir) as it stands; the extra negation made every attenuation 0 and the surface came out black.

tev-outline
match (diff 2.1)
pe0
vi0
CP 0x201		okFIXED by this sweep: the model and its cartoon outline render.
Source: Tev/tev-outline.c - the scene is drawn with per-object IDs in the alpha plane, the plane is copied out as an a8 texture with GXCopyTex and a screen-sized quad compares the ID map with a shifted copy of itself through the TEV and the alpha function.
Four bugs, all fixed:
  - src/cp.cpp: an indexed XF block load (GXLoadPosMtxIndx and friends) read the matrix out of the index array without byte-swapping it - the array is guest memory and every other word the CP reads through an array is swapped in FetchComp - so every per-ring matrix was garbage and the model was invisible.
  - src/pe.cpp/h: the texture copy's destination format is the copy engine's own 4-bit set, not the texture unit's TexFormat. The single-channel formats (a8 and friends) are packed now, so the ID map is written at all.
  - src/pe.cpp: the EFB read-back carried only the three colours; the single-channel copy formats need the alpha plane, so ReadEfb returns RGBA now and the SDL context asks for an alpha channel.
  - src/tev.cpp: an unclamped stage keeps an 11-bit signed result, but what the alpha function compares is the low 8 bits of the completed alpha. The demo subtracts two texture lookups and relies on the two's complement wrap to see the same edge from either side.
